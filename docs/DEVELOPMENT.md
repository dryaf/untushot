# Developing UntuShot

UntuShot is a Rust/GTK 3 application. The editor, exported PNG and clipboard image
share the Cairo rendering path. There is no browser or Electron runtime.

## Build and run

```sh
cargo build --release --locked
./target/release/untushot --demo
```

Rust 1.75+, GTK 3.24+ development files and `pkg-config` are required. Use `--offline`
when dependencies are already available locally. `--demo` opens synthetic sample
content without taking a desktop screenshot or browsing personal screenshot files.

## Checks

```sh
make test                 # Formatting, backports, Rust tests, Clippy, installer tests
make test-ux              # Editor workflows and a 30-layer editing session
make test-clipboard       # PNG/JPEG transport on a private display
make test-languages       # English, German, French and Spanish UI checks
make audit                # Backports, optimized security tests and OSV scan
```

The GUI harness uses **Broadway**, isolated XDG directories and an in-memory
settings backend. Install `broadwayd` with your distribution's GTK 3 tools.
The harness never connects to your desktop display or clipboard.

The editing-session test exercises 140 document changes, including ten text
sessions, and traverses the complete 100-step retained undo/redo history. It then
compares editable layers and rendered pixels across project save/reopen, PNG,
clipboard transfer and session recovery. `target/ux-audit.json` contains the
results and CPU timings; those timings are not desktop frame-rate measurements.

Hardware acceptance is separate: real mixed-DPI capture, monitor hotplug,
compositor behavior, portal permissions and tray integration need a real desktop.
GTK3-compatible security backports and their provenance are documented in
[the vendor notes](../vendor/README.md).

## Localization

The application embeds [messages.json](../locales/messages.json). German source
messages identify each entry; every entry has English, French and Spanish values.
No runtime catalog installation is needed.

- `crate::i18n::tr("source message")` translates static UI strings.
- `crate::i18n::format!("template {value}")` compiles **all four** format variants
  with Rust's formatter. Named captures, argument types and format specifications
  are checked at build time.
- Localized `anyhow!`, `bail!`, `ensure!`, `println!` and `eprintln!` wrappers handle
  application errors and CLI output through the same catalog.
- The GTK UI is translated at the call site. User text, layer names, file paths,
  project data, command names, JSON keys and widget identifiers are not translated.
- Tool metadata remains constant; its display names are translated when shown.
- GTK's own stock widgets use the desktop's installed GTK translations.

Locale selection checks `LANGUAGE` first (including colon-separated preferences),
then `LC_ALL`, `LC_MESSAGES` and `LANG`. Regional identifiers such as `fr_CA.UTF-8`
and `es-MX` map to their base language. Unsupported locales fall back to English.
The language is selected once per process; restart the background instance after
changing the desktop language.

Run the UI checks separately for each language:

```sh
python3 tools/test_clipboard.py --suite localization --language en
python3 tools/test_clipboard.py --suite localization --language de
python3 tools/test_clipboard.py --suite localization --language fr
python3 tools/test_clipboard.py --suite localization --language es
```

Each check verifies localized labels and that user-supplied layer names remain
unchanged. It writes `target/locale-<language>.png` for visual review. Existing
German-language workflow assertions run with the harness's explicit German
locale; the documentation recorder always requests English.

Desktop-entry actions and comments have English defaults and `de`, `fr`, `es`
translations in both the template and installer output.

## Regenerating the feature GIFs

Requires `broadwayd` and `ffmpeg`, in addition to the normal build dependencies.

```sh
make showcase
# Equivalent: python3 tools/render_showcase.py --record
```

The recorder in [showcase.rs](../src/ui/showcase.rs) drives the production GTK
controls, document operations and gesture handlers. It draws the actual widgets
into PNG frames and adds English captions outside the application window. Sample
images are generated by Cairo; no personal images, browser sessions or desktop
captures are used.

- Temporary frames and timing manifests: `target/showcase-frames/`.
- Checked-in animated GIFs: `docs/media/`.
- Titles, duration, source frame count and file sizes: [media manifest](media/manifest.json).
- Run `python3 tools/render_showcase.py` without `--record` to re-encode existing
  frames using a shared per-clip palette and optimized changed rectangles.

The menu recordings show actual application menus in an isolated preview, drawn
at their natural size because headless Broadway has no physical screen for popup
placement. It can emit GTK geometry/device warnings during this preview.
`UNTUSHOT_SHOWCASE_SECTION=menus` records only the menu and layer-space clips. Monitor
layouts and incoming capture images are fixtures. The web-page demo starts with
an image placed on the isolated clipboard, not an automatically captured browser
tab. These distinctions are also stated in the README.

## Installation and desktop integration

```sh
make install
make install DESKTOP_INTEGRATION=off
make desktop-install
make install PREFIX=/usr DESTDIR=/tmp/untushot-package
make uninstall
```

Run the local installer as your normal user. By default it installs:

| Item | Location |
| --- | --- |
| Launcher | `~/.local/bin/untushot` |
| Application binary | `~/.local/libexec/untushot` |
| Desktop entry and icons | `~/.local/share/` |
| GNOME integration backup | `~/.config/untushot/desktop-integration.json` |
| Autostart entry | `~/.config/autostart/io.github.untushot.UntuShot.desktop` |
| Background log | `~/.local/state/untushot/background.log` |

The supported GNOME integration binds Ctrl+Shift+X, enables login autostart and
starts the tray process. It records previous shortcut values and restores them on
uninstall if they have not since been changed by the user. Staging with `DESTDIR`
does not modify a live desktop session. Projects, recovery data and preferences
remain after uninstall.

The tray needs `libayatana-appindicator3-1` and desktop support for AppIndicator.
On Ubuntu/GNOME this commonly includes the Ubuntu AppIndicators extension. Other
desktops can bind the capture command themselves, for example in Sway:

```text
bindsym Ctrl+Shift+x exec ~/.local/bin/untushot --capture region --backend grim
```

The installer recognizes an earlier installation of this project under its former
name, Rustshot, and migrates its owned configuration, recovery files and thumbnail
cache without overwriting existing UntuShot data. It does not remove an unrelated
application with that name.

## Capture behavior and limits

- `grim` requires compositor screencopy support. The portal delegates capture
  selection and permissions to the desktop.
- Direct multi-monitor capture uses a common pixel grid based on the highest GDK
  scale. Lower-scaled displays are upscaled. GTK 3 exposes integer render scales;
  mixed/fractional scaling is not a native 1:1 pixel map for every display.
- Portal screenshots do not contain monitor coordinates, so UntuShot does not
  invent exact monitor presets for them.
- Changed monitor arrangements stop a pending capture so the source can be
  checked again. Missing monitor IDs do not silently capture the full desktop.
- Canvas: up to **64 megapixels**, **32,767 pixels per side**.
- Clipboard page import: up to **32 MiB** encoded data, **40 megapixels** and
  **32,767 pixels per side**.
- Document history: **100 steps**. Images are shared between snapshots; image
  admission accounts for the undo/redo states that remain after the new edit.
- Text history: separate while editing, bounded by step count and retained text
  payload. Applying the session creates one document step; Escape discards it.
- Layer-render preview cache: **64 MiB**. Screenshot thumbnails: **256 cached
  previews**, with up to **60 recent PNG/JPEG files** shown in the history strip.

A project retains the original image, including areas hidden by redaction layers.
PNG and clipboard output contain the rendered, opaque redaction. Share the
rendered output when you intend to share only the visible result.
